## Validated Proposals

| Proposal | Rationale |
|---|---|
| Explicit binary transcript containing versions, UUIDs, device names, roles, public keys, and nonces | MAC and HKDF derive across an identical, canonical sequence on both ends without dependence on JSON key serialization order |
| Separate `K_c2s`, `K_s2c`, `K_confirm`, explicit HKDF info labels, 32-byte key lengths | Separation of directions and key domains |
| `K_pin = HKDF(PIN, salt: K_confirm, info: …)` | Secret salt prevents offline dictionary attacks against PIN over captured wire traffic |
| Mandatory `serverProof` in `paired` and `authOk` | Client authenticates proof of possession of PIN/token; successful decryption alone is insufficient |
| Initial server confirmation is encrypted; subsequent frames use AEAD | Tokens are never transmitted in plaintext; transition to `connected` follows proof verification |
| Independent 96-bit big-endian frame counters; rejection of repeats and overflow | Prevents nonce reuse with ChaCha20-Poly1305 |
| 65,536-byte message payload limit; up to 65,508 bytes plaintext JSON in protected frames | Accounts for 12-byte nonce and 16-byte authentication tag |

The formulas refine existing schemes without introducing third-party dependencies.
Verified against `CryptoKit.swiftinterface` in macOS 26.5 and iOS 26.5 SDKs.
RFC compliance: RFC 7748 (X25519), RFC 5869 (HKDF), RFC 8439 (ChaCha20-Poly1305).
